# Мониторинг нод Remnawave

Статус серверов в телеграме: жив ли сервер, что с процессором и памятью,
сколько реально идёт трафика и не режет ли хостер порт.

## Как это устроено

Три источника вместо одного — потому что по отдельности каждый врёт:

| Источник | Что знает | Чего не знает |
|---|---|---|
| **Панель Remnawave** | онлайн-юзеры, трафик, «вижу ли я ноду» | что с железом; почему нода не отвечает |
| **Агент на ноде** | ЦП, ОЗУ, диск, сеть, скорость порта | видно ли ноду снаружи |
| **Пробники NL + РФ** | доступна ли нода и открыт ли порт xray | что внутри сервера |

Главная польза — в пересечении. Панель говорит «не вижу ноду», агент говорит
«я жив» → железо в порядке, надо перезапустить xray, а не ехать к хостеру.
Из NL пингуется, из РФ нет → IP зарезан ТСПУ, сервер трогать не нужно.

```
    ноды (node_exporter, только в WireGuard-сети)
             │
             ▼
   ХАБ (дедик NL): vmagent → VictoriaMetrics → vmalert → Alertmanager → бот
             ▲                                                            │
             │ пингует ноды из РФ                                         ▼
   ПРОБНИК (сервер панели)                                          Telegram
```

## Структура

```
hub/           всё, что крутится на дедике в NL
  bot/         телеграм-бот: витрина + приёмник вебхуков
  vmalert/     правила алертов — что считать аварией
  data/        ЕДИНСТВЕННОЕ место, где лежит состояние
prober/        пробник для РФ (ставится на сервер панели)
ansible/       раскатка агента на ноды
targets/       nodes.yml  — все ноды панели, цели для проверок доступности
               agents.yml — только ноды с раскатанным агентом
```

## Установка

### 0. Приватная сеть

Всё внутреннее общение идёт по WireGuard: хаб — сервер, панель и ноды — клиенты.
Tailscale не используется намеренно: его сайт и управляющие серверы недоступны
из РФ, а путь доставки алертов не должен зависеть от того, что могут заблокировать.

На хабе один раз:

```bash
./scripts/wg-hub-init.sh <публичный_IP_хаба> 51820
```

Затем на каждого клиента:

```bash
./scripts/wg-add-peer.sh panel-ru 2     # сервер панели → 10.77.0.2
./scripts/wg-add-peer.sh nl-1 11        # нода          → 10.77.0.11
```

Скрипт печатает готовый конфиг. Для панели — положить его в
`/etc/wireguard/wg0.conf` и запустить `wg-quick@wg0`. Для нод — сложить файлы
в `ansible/files/wg/<имя_ноды>.conf`, дальше их разложит `make deploy`.

### 1. Хаб (дедик NL)

```bash
git clone <repo> && cd vpn-monitoring/hub
cp .env.example .env && $EDITOR .env
# Логин и пароль METRICS_* из .env панели, строго без перевода строки
printf '%s' 'METRICS_USER' > secrets/panel_metrics_user
printf '%s' 'METRICS_PASS' > secrets/panel_metrics_password
chmod 600 secrets/panel_metrics_*
```

Адреса панели и пробника задаются в `.env` (`PANEL_ADDR`, `RU_PROBER_ADDR`) —
в `scrape.yml` их править не нужно, иначе правку затрёт первый же `git pull`.

```bash
make up
```

### 2. Пробник (сервер панели, РФ)

```bash
cd prober && PROBER_PRIVATE_IP=10.77.0.2 docker compose up -d
```

### 3. Ноды

```bash
cp ansible/inventory.example.yml ansible/inventory.yml && $EDITOR ansible/inventory.yml
make deploy
```

### 3.5. Список нод из API панели

Хаб спрашивает у панели список нод: скриптом `make sync-nodes` — для проверок
доступности, и ботом раз в минуту — чтобы знать, какие ноды выключены намеренно
и не поднимать по ним ложных тревог.

Ходить за этим лучше по приватной сети: `PANEL_API_URL_<ПРОЕКТ>=http://10.77.0.5:3000`.
Тогда запрос не зависит от домена, а токен не уходит в интернет. Remnawave 3.x
при этом проверяет, что перед ней обратный прокси с HTTPS, и голый HTTP молча
обрывает — `curl` показывает это как `Empty reply from server`, а сама панель
пишет в лог `Reverse proxy and HTTPS are required`. Лечится указанием домена:

```
PANEL_API_HOST_<ПРОЕКТ>=panel.example.com
```

Хаб добавит его в `Host` и допишет `X-Forwarded-Proto: https`. Порт 3000
панели нужно опубликовать на адресе WireGuard — в её `docker-compose.yml`
строкой `- '10.77.0.5:3000:3000'` рядом с уже имеющейся для 127.0.0.1.

Можно оставить и публичный домен, но если он за Cloudflare, тот ответит
челленджем `Just a moment...` вместо API. Тогда нужно правило WAF → Skip
для `/api/*`.

#### Ноды за NetBird и другими оверлеями

Если панель ходит к ноде через NetBird, в API у ноды адрес вида
`100.113.x.x`. Снаружи он не пингуется: хаб в эту сеть не входит, и нода
выглядела бы упавшей, хотя на ней сидят пользователи. Поэтому адреса из
диапазонов `OVERLAY_RANGES` (по умолчанию `100.64.0.0/10`) `make sync-nodes`
не проверяет, а ищет их реальный IP.

Проще всего отдать это самому NetBird: его API знает для каждого пира и
адрес в сети NetBird, и белый IP, с которого пир подключён. Токен создаётся
в NetBird: Team → Service Users → новый сервисный пользователь → Create Token.
Роль ему нужна та, что видит все пиры: обычному пользователю NetBird
может показывать только его собственные.

```bash
printf '%s' 'nbp_...' > hub/secrets/netbird_api_token && chmod 600 hub/secrets/netbird_api_token
```

Если IP нужен другой — например, xray слушает дополнительный адрес, —
его можно задать руками в `targets/public-ip-overrides-<проект>.conf`,
эта строка важнее NetBird:

```
aeis = 203.0.113.11
```

Ноды, для которых IP не нашёлся ни там, ни там, скрипт перечисляет в конце
вывода, проверки по ним выключены. Адрес в самой панели менять не нужно — иначе она пойдёт к ноде
мимо NetBird.

Список целей сам не обновляется: после правок в панели или в этих файлах
запустите `make sync-nodes` ещё раз.

### 4. Вебхуки в панели

В настройках Remnawave: URL `http://<приватный_IP_хаба>:8080/remnawave`,
секрет — тот же, что в `REMNAWAVE_WEBHOOK_SECRET`. Публичный домен не нужен,
панель достучится по приватной сети.

## Добавить ноду

Дописать блок в `targets/nodes.yml` и прогнать `make deploy LIMIT=имя`.
vmagent перечитывает список сам раз в 30 секунд, перезапускать ничего не надо.

## Переезд на другой сервер

Это спроектировано так, чтобы переезд занимал пять минут: всё состояние
лежит в одном каталоге `hub/data`, конфигурация — в git, ничего не
разбросано по системе.

```bash
# на старом
cd hub && docker compose down
tar czf /tmp/vpnmon.tgz -C ../.. vpn-monitoring
# на новом
tar xzf vpnmon.tgz && cd vpn-monitoring/hub && docker compose up -d
```

Если менялся приватный IP хаба — поправить `HUB_PRIVATE_IP` в `.env` и адрес
вебхука в панели. На нодах поменяется только endpoint в `/etc/wireguard/wg0.conf`,
если у нового хаба другой публичный IP.

История метрик переносится вместе с `hub/data/victoriametrics`. Если она не нужна — исключите этот каталог и переезд станет мгновенным.

## Когда бот пишет и когда молчит

Звук — только когда нужно что-то делать. Всё прочее приходит тихо или не
приходит вовсе.

| Уровень | Первое сообщение | Напоминания | Отбой |
|---|---|---|---|
| critical — сервер лёг, блокировка из РФ, панель потеряла ноду | со звуком, в любое время | по нарастающей, `REPEAT_STEPS` | тихо, в той же карточке |
| warning — диск, процессор, канал, порт xray, флап связи | со звуком, ночью тихо | раз в `WARNING_REPEAT_HOURS` | тихо, в той же карточке |
| info — молчит агент, нет свежего замера скорости | тихо | нет | нет |
| `notify: once` — разовые события: частые перезагрузки, смена скорости линка | по уровню | нет | нет |

**Одна проблема — одно сообщение.** Бот ведёт по каждой проблеме карточку
и не плодит её версий:

- напоминание и новая нода в той же аварии присылают карточку заново внизу
  ленты, со звуком, а старую убирают;
- поднявшаяся нода зачёркивается в карточке без звука;
- отбой превращает карточку в «✅ отбой» с длительностью, тоже без звука.

Тихие перемены правят карточку на месте, если она последняя в ленте, иначе
переносят её вниз: правку сообщения выше никто бы не заметил. Telegram даёт
боту убирать свои сообщения только первые 48 часов — карточка старше
останется в ленте, а новая придёт ниже.

Нагрузка (процессор, память, steal, канал, дропы) держится в тревоге ещё
15 минут после того, как спала (`keep_firing_for`). Иначе процессор,
болтающийся около порога, даёт «сработал» и через минуту «отбой» по кругу.

**Перезагрузка аварией не считается.** О потере связи `PanelNodeDisconnected`
и `NodeDown` сообщают, только если нода не вернулась за пять минут, —
сервер, который перезагрузился и поднялся сам, не даёт ни одного сообщения.
Писать стоит, когда перезагрузки повторяются: `NodeRebootsFrequently`
срабатывает на вторую за сутки. Мгновенные вебхуки панели о потере
и восстановлении связи в чат по той же причине не идут.

Ночной режим — `QUIET_HOURS` по Москве, по умолчанию с 0 до 8.

## Команды бота

| Команда | Что делает |
|---|---|
| `/status` | сводка по всем нодам, кнопка «Обновить» |
| `/node nl-1` | подробности: доступность с двух точек, ресурсы, канал, p95 |
| `/mute nl-1 2ч` | полная тишина по ноде: не придёт ничего (плановые работы) |
| `/mutelink inmb 30д` | тишина только про разрывы связи, остальное по ноде приходит |
| `/mutes` | что сейчас заглушено и сколько ещё будет молчать |
| `/unmute nl-1` | снять с ноды обе заглушки |

Срок пишется как `30м`, `2ч`, `7д`, `2н`; без него — 2 часа для `/mute`
и 7 дней для `/mutelink`. Голое число считается часами.

Имя ноды ищется по части и без учёта регистра: `/mutelink frankfurt` найдёт
`DE Frankfurt 1`. Имя с пробелами лучше брать в кавычки — `/mute "DE Frankfurt 1" 3ч`, —
иначе последнее слово может быть принято за срок. Целиком набранное имя
кавычек не требует: точное совпадение всегда важнее догадки о сроке.

### Кнопки под сообщением об аварии

Под каждым алертом — ряд кнопок: «🔇 2 ч.», «🔇 8 ч.», «🔇 24 ч.», «🔇 2 дн.».
Это пауза ровно по этой проблеме на этих нодах: `NodeFlapping` на `inmb`
замолчит, а про упавший сервер на той же ноде напишут. Сообщение при этом
подписывается «на паузе» и получает кнопку «🔔 Продолжить уведомлять»:
она снимает паузу и начинает цикл напоминаний с начала — первое сообщение
придёт сразу, дальше по нарастающим паузам `REPEAT_STEPS`.

Паузы живут там же, где заглушки, и видны в `/mutes`. Снять можно и
командой: `/unmute <имя ноды>`.

Кнопки помнит сам бот, и память у него только в оперативной: после
перезапуска кнопки под старыми сообщениями отвечают, что не помнят, к чему
относятся, — следующее напоминание придёт с рабочими. Состояние можно было
бы сложить на диск, но тогда перезапуск переставал бы быть безопасным
действием, а это слишком дорогая плата за кнопки в старых сообщениях.

### Что именно глушит лёгкая заглушка

`NodeFlapping`, `PanelNodeDisconnected` и `PanelLostNodeButHostAlive`. Всё остальное по этой ноде — упавший
сервер, блокировка из РФ, кончающийся диск — доходит как обычно. Это для
известной и пока нерешаемой болячки: чтобы не мозолила глаза, но и не уносила
с собой настоящие аварии.

Обе заглушки живут в Alertmanager (`hub/data/alertmanager`) и переживают
перезапуск. Оставшиеся вебхуки панели (порог трафика, включение и выключение
ноды) идут мимо Alertmanager, поэтому полную заглушку для них бот проверяет сам.

## Сторож

`Watchdog` раз в 15 минут пингует внешний сервис (`HEALTHCHECKS_URL`).
Если хаб умрёт целиком, пинги прекратятся и вам напишут снаружи.
Без этого тишина в чате неотличима от «всё хорошо» — а это самый обидный
способ проспать аварию.

## Что не сделано (v2)

- Проверка «пробить ноду настоящим xray-клиентом из РФ» — ловит случаи,
  когда ICMP и TCP проходят, а протокол режется DPI.
- Дашборды Grafana (`docker compose --profile grafana up -d` поднимет пустую).
- История смен IP при блокировках.
